# 개발 흐름과 실패한 시도

## 목표

수식이 포함된 문제와 해설을 자유롭게 편집하고, 해설을 미주로 관리할 수 있는 한글 문서를 만드는 것.
처음에는 **이미지·PDF 문제 자료를 곧바로 한글로** 바꾸는 것이 목표였다.

## 1. v0 — 이미지/PDF → 한글 직접 변환 (보류)

`legacy/v0-init/`

* 입력: 사진/PDF 를 보고 손으로 옮겨 적은 `TEXT:` / `EQ:` / `EQALIGN:` 파일 하나.
* 처리: `win32com` 으로 한글을 열고 `EquationCreate` 로 수식 객체를 넣는다.
* 얻은 것: 수식이 그림이 아니라 **편집 가능한 수식 객체**로 들어가려면 `HEqEdit.string` + `TreatAsChar=1` + `Version="Equation Version 60"` 조합이 필요하다는 점. hwpx 로 저장한 뒤 XML 을 비교해 정상 수식 객체와의 차이를 찾아냈다.
* 막힌 이유: OCR(사진에서 LaTeX 로) 단계의 오류와 변환(LaTeX 에서 한글로) 단계의 오류가 섞여 어느 쪽이 틀렸는지 가릴 수 없었다. 수식 변환기(`latex_to_hwp.py`)도 딕셔너리 순서대로 `str.replace` 하는 구조라 `\int` 가 `\in` 에 먹히는 식의 충돌이 있었고, 표에 없는 명령은 소리 없이 사라졌다.
* 결정: **OCR 을 분리**하고, 검증 가능한 LaTeX 입력을 기준으로 변환 파이프라인을 먼저 완성한다. 이미지·PDF 는 LaTeX 로 옮긴 뒤 넣는다.

## 2. tex 파서와 DSL

* `.tex` 원고를 읽어 문제 헤더(`\noindent\textbf{예제 3-1. …}`), 해설 헤더, 인라인/디스플레이 수식, 목록 환경을 인식하고 DSL 로 낸다.
* 해설은 `SOL:` … `ENDSOL:` 로 감싸 미주로 넣는다.
* 재번호 매김과 교차 참조 치환, 그림 메모 이동, 여러 tex 이어 붙이기가 이 단계에서 붙었다.
* 수식 변환기는 `\[A-Za-z]+` 토큰 단위 정규식 치환으로 다시 썼다. 접두사 충돌이 구조적으로 없어졌고, 표에 없는 명령은 "미지원" 으로 모아서 마지막에 출력한다.
* 남은 문제: 한글 COM 은 문서가 커질수록 느려진다(체감상 줄 수의 제곱). 대규모 원고 하나를 한 번에 돌리면 수 시간이 걸렸다.

## 3. v3 — hwpx 직접 생성 (실패)

`legacy/v3-hwpx-attempt/` (당시의 변환 스크립트만 보관. hwpx 를 쓰는 코드 자체는 남기지 않았다)

속도 문제를 피하려고 **한글 없이** hwpx(XML zip)를 직접 쓰는 방법을 시도했다.

**되는 것.** 파일 구조, 문단, 미주, 수식 컨트롤 모두 정상 생성되어 한글에서 열렸고, 전체 변환이 0.8초에 끝났다.

**막힌 것: 한글은 수식 크기를 열 때 다시 계산하지 않는다.**
hwpx 의 `hp:equation` 에는 스크립트와 함께 `hp:sz`(폭·높이)와 `baseLine` 이 저장되고, 한글은 이 값을 그대로 레이아웃에 쓴다. 재계산은 수식 편집기를 열었다 닫을 때만 일어난다. 따라서 파일을 직접 쓰는 쪽이 정확한 크기를 미리 알아야 하는데, 그 크기는 한글 수식 엔진(HYhwpEQ 글꼴, 분수·첨자·괄호 배치 규칙)이 결정하는 것이라 외부에서 재현할 수 없다.

* 증상: 처음 넣은 추정 폭이 실제보다 작아 `a,b를`, `2r+1인` 처럼 인라인 수식이 뒤 글자와 겹쳤다. 샘플 실측값으로 계수를 보정하면 겹침은 줄지만 여전히 근사치라 여백이 들쭉날쭉하고, 수식 하나를 편집하면 그것만 정확해져 문서 전체의 일관성이 깨진다. hwp 로 변환해도 저장된 값이 그대로 가므로 해결되지 않는다.
* 근본 한계: 정확한 크기를 얻으려면 결국 한글이 한 번은 계산해야 한다. 스크립트→크기 표를 만들려면 한글이 저장한 파일이 필요하고, 그걸 만드는 방법이 곧 COM 방식이다. 즉 hwpx 직접 생성은 COM 을 대체하는 게 아니라 **COM 결과에 의존하는 캐시**가 되어, 목표였던 "한글 없이 끝내기" 가 성립하지 않는다.
* 부수적 제약: `\mathcal` 처럼 한글 수식에 대응 키워드가 없는 명령은 유니코드 문자나 굵은 글자로 대체해야 하고, 미주 안의 쪽 나누기는 의미가 없어 무시했다. 이건 방식의 문제라기보다 변환기 수준의 제약이다.

**결론.** 문서를 한두 번만 뽑을 거라면 장별로 나눈 COM 방식이 현실적이다. 자주 재생성해야 할 때만 "COM 한 번 → 크기 표 추출 → hwpx 즉시 생성" 조합이 의미가 있다.

## 4. 현재 — 분할 COM 방식

`src/`

* COM 방식으로 복귀. 대신 DSL 을 문제 경계에서 3,000 줄 안팎으로 쪼개(`split_dsl.py`) 각각 hwp 로 만든 뒤 끼워넣기로 합친다(`merge_hwp.py`). 조각 하나는 몇 분이면 끝난다.
* `make_hwp_from_txt.py` 에서 고친 것: EnsureDispatch 가 이미 빈 문서를 만들어 문서가 2개 열리던 문제, 종료 시 "저장하시겠습니까" 팝업, 미주 첫 줄이 비면 안 되는 제약(`PROB:`/`SOL:` 직후의 `BR:` 을 DSL 단계에서 제거), 한국어 조사 때문에 수식 뒤 공백을 넣을지 말지 결정하는 규칙(한글로 시작하면 붙임).
* `--attach` 로 이미 만들어진 hwp 의 `N.` 문항에 미주와 그림을 나중에 덧붙일 수 있다. 문항 위치는 `hwp_read.py`(한글 없이 hwp 를 읽는 최소 파서)로 찾는다.
* 검증: 실제 원고(문제 수백 개)에서 문제/해설 1:1 대응, 수식 6,000여 개 변환 실패 0. hwp 생성은 윈도우에서 실측.
